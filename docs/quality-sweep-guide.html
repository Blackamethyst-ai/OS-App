02 / Deep Dive

How It Works

Five autonomous phases, each with a clear scope and an independent commit. Every phase verifies the build before moving on.

1
Baseline
  • Runs lint, test suite, and build to establish the reference state
  • Documents current error count, test count, and build status
  • Auto-detects the project's toolchain from package.json / pyproject.toml
# Adapt to the project's stack automatically
npm run lint 2>&1 | tail -100
npm run test:run 2>&1 | tail -40
npm run build 2>&1 | tail -20
No commit — measurement only
2
Lint Fixes
  • Runs auto-fix with eslint --fix (or equivalent linter)
  • Manually resolves remaining errors: unused imports, missing keys, type errors, a11y warnings
  • Verifies tests still pass after all lint fixes
npx eslint . --fix
# Target: 0 lint errors
npm run test:run # verify no regressions
Commit: "fix: resolve all lint errors"
3
Test Coverage
  • Spawns parallel background agents — each gets 2-3 specific files to test
  • Prioritizes: hooks/composables → core services → pure utilities
  • Each agent runs the test suite to verify its work; full suite runs after all agents complete
# Agent spawning pattern
Agent({
  mode: "bypassPermissions",
  subagent_type: "general-purpose",
  run_in_background: true,
  prompt: "Write tests for useAuth.ts, useSession.ts. Run vitest to verify."
})
Commit: "test: add coverage for hooks and services"
4
Dead Code Removal
  • Uses targeted bash loops to find orphaned files — never Explore agents (context limit risk)
  • Checks App.tsx and entry points for lazy/dynamic imports before deletion
  • Runs vite build after each deletion batch to verify nothing breaks
# Find orphaned components
for f in components/*.tsx; do
  name=$(basename "$f" .tsx)
  count=$(grep -rl "$name" --include="*.tsx" . | \
    grep -v node_modules | grep -v "$f" | wc -l)
  if [ "$count" -eq "0" ]; then echo "DEAD: $f"; fi
done
Commit: "chore: remove 1,590 lines of dead code"
5
Security Audit
  • Runs npm audit fix (or pip-audit, cargo audit, etc.)
  • Verifies build and tests still pass after patching
  • Reports total vulnerabilities fixed by severity
npm audit fix
npm run build # verify
npm run test:run # verify
Commit: "fix: patch 7 security vulnerabilities"

Weekly Hygiene

Run in PR checks to enforce code quality gates. Block merges that introduce new lint errors or vulnerabilities.

05 / Agent Intelligence

How Agents Are Orchestrated

Quality sweeps use Claude Code's background agent system for parallel test writing — with strict scoping rules learned from production incidents.

  • Parallel spawning — multiple test-writing agents run simultaneously, each targeting 2-3 specific files
  • Well-scoped tasks — every agent prompt includes exact file paths, the test runner command, and a verification step
  • Automatic fallback — if an agent fails or hits context limits, the work is done directly instead of re-spawning
  • Permission pre-flight — verifies Write, Edit, Bash(*) permissions before spawning any agent
  • Anti-pattern avoidance — never uses Explore agents for 500+ file codebases (context overflow)

✓ Patterns That Work

Test writer A + Test writer B
Different files, no conflicts
Test writer + Dead code scanner
Read-only scan + write tests
Build + Lint + Test
All read-only, independent checks

✗ Patterns That Break

Two agents editing the same file
Race condition — data loss risk
Explore agent on 500+ files
Context overflow — agent crashes
Agent depending on another's output
No inter-agent communication
⚠ Operational lesson (OS-App, March 2026): Two Explore agents failed with "prompt too long" on a 497-file codebase. Direct bash loops completed in seconds. Always prefer grep -rl loops over Explore agents for dead code detection.

06 / Configuration

Required Setup

Quality sweep runs autonomously, but it needs the right permissions to spawn background agents.

~/.claude/settings.json

The following permissions must be in the allow list for agents to function.

{
  "permissions": {
    "allow": [
      "Read",
      "Write",
      "Edit",
      "Bash(*)"
    ]
  }
}
Warning: Without these permissions, background agents fail silently. The sweep will appear to run but agents produce no output. Always verify permissions before the first run.

07 / FAQ

Frequently Asked Questions

Q Does it modify my architecture?
No. Quality sweep only applies quality fixes — lint errors, test coverage, dead code, and security patches. It never refactors architecture or changes business logic.
Q What if it breaks something?
Each phase commits separately, so you can revert any individual phase with git revert. The sweep also verifies build + tests after every phase before committing.
Q Does it work on non-JavaScript projects?
Yes. It auto-detects the stack from config files: package.json (npm/yarn), pyproject.toml (pytest/ruff), Cargo.toml (cargo), and adapts commands accordingly.
Q How long does it take?
Typically 5-15 minutes depending on codebase size. Parallel agent spawning for test writing is the main time saver compared to sequential execution.
Q Can I run individual phases?
Not yet as a standalone feature — but since each phase commits independently, you can stop after any phase and the completed work is preserved.
Q What about monorepos?
Target a specific subdirectory: /quality-sweep packages/core. The sweep scopes all operations to that directory.
Q Will it delete code I need?
It only removes files with zero imports anywhere in the project. It also checks entry points for lazy/dynamic imports, and always verifies with a full build before committing any deletion.
